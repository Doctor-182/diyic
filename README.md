# VRChat 实时同传（vrdub）

把我说的中文**边说我边用日语说出来**（我的克隆音色），把对方说的日语**实时变中文字幕**，对方打的字**识别成中文浮在原文位置**。
延迟：**我说完最后一句 → 对方听到日语，中位 0.46–0.85 s，长句最差 p90 1.1–2.7 s（最好的一句 0.17 s，部分句子我还没说完就开口了）**；对方说完 → 中文字幕 **0.30 s**。这是本机 8 次评测的分布（p50 0.46 / 0.48 / 0.55 / 0.63 / 0.84 / 0.85 / 1.38 s；p90 1.11–2.73 s），抖动几乎全来自云端 ASR 与 TTS 首包（ASR 0.4–3.2 s、TTS 0.74–1.20 s），逐句数据在 `out/bench.md`。

不用点任何按钮就能用：双击 `run.bat` → 浏览器打开控制台 → 直接对着麦克风说话。

> **依赖**：Python 3.12 + `numpy / pyaudiowpatch / onnxruntime / rapidocr-onnxruntime / opencv-python / Pillow / PySide6`（锁版本见 `requirements.txt`；也可以把依赖装进项目下的 `.pylibs\`，脚本会自动优先用它）。本地模型在 `models\`，缺什么跑 `python tools/fetch_models.py --check`。云端 key 放 `%LOCALAPPDATA%\VRDub\config\.env.local`（首次启动会把项目目录里的 `.env.local` 自动搬过去），变量名见 `.env.example`。三件套全部走套餐端点，不额外计费。

> **用户数据在哪**：配置 `%LOCALAPPDATA%\VRDub\config\settings.json`、日志 `%LOCALAPPDATA%\VRDub\logs\`、截图与语料 `%LOCALAPPDATA%\VRDub\out\`。程序目录只读也能跑（装在 `C:\Program Files` 里不会丢配置），整个 `VRDub` 目录删掉等于恢复出厂。

## 项目结构

```
vrdub/            程序本体（一个包，一条进程起全部）
  app.py          装配与生命周期：设备绑定、子进程、HTTP 服务、看门狗
  chains.py       A/B 两条链的调度核心（分句、投机识别、排队、回声判定）
  asr*.py         识别：本地 SenseVoice / 云端 qwen-audio / anime-whisper 备选
  mt.py tts.py    翻译（流式子句）与合成（套餐 tts-plus，克隆音色 t3）
  ocr*.py         C 链：GDI 截屏 → PP-OCRv4 双模型路由 → 原位气泡
  hud.py danmaku.py   浮窗与弹幕（独立 Qt 进程，抓屏不可见）
  paths.py cfg.py     路径策略与配置（用户目录 / 热改 / 迁移）
  server.py bus.py    标准库 HTTP + SSE，单机只绑 127.0.0.1:8899
  web/            控制台（纯静态，无构建步骤）
scripts/          启动/自检/评测/守护脚本（_env.bat 统一探测解释器）
tools/            长期工具：延迟报表、模型检查、设备探针、注入测试
tools/dev/        一次性探针（调试记录，随时可删）
tests/            真值表：回声判定、云端优先、语言闸、翻译质量
models/           本地模型（权重不入库，见 tools/fetch_models.py）
docs/             架构、协议、部署、UI、选型与路线图
```

## 1. 一分钟上手

1. **装 VB-CABLE**（虚拟声卡，一次性）：装完系统里会多出 `CABLE Input`（放声音进去）和 `CABLE Output`（取声音出来）。
2. **VRChat 的声音设置**：麦克风 = `CABLE Output`；扬声器随便（耳机）。
3. **Windows 声音设置**：默认播放设备保持耳机，默认录音设备保持你的真麦。
4. 双击 `run.bat`。控制台里设备应显示：麦克风 `麦克风 (你的耳机)`、输出 `CABLE Input`、我的监听 `扬声器 (你的耳机)`；B 链的来源不是设备而是**进程**（日志：`B 链只听 VRChat 进程 pid=xxxx`）。
5. 先在控制台点「试听」——耳机里听到日语 = TTS 通了；再点「回环自测」——表格里冒出 A 链中文→日语两行 = 整条链路通了。
6. 进 VRChat 说话。别人听到的是日语，你自己在浮窗里看到中文原文 + 日语译文。

**启动就一个图标**：桌面上的「VRDub 无言势」= 后端在跑就直接开控制台页面，没跑就隐藏窗口起 `run.bat nobrowser`、等它就绪再开浏览器（不会闪黑框）。这个图标跑的是 `scripts\打开控制台.vbs`；丢了就双击 `scripts\建桌面快捷方式.ps1` 重新生成。安装包版则在开始菜单「VRDub」。

**监听（自己听得见合成音）**：合成音默认同时放两路—— `CABLE Input`（给 VRChat 送出去）和你的耳机（`我的监听` 选的设备）。
所以日语念出来的时候你自己也听得见，能当场判断音色/语速对不对。控制台「监听开关」关掉就只剩虚拟线（纯给别人听）。
日志里应有两行：`播放开 #19 CABLE Input` 和 `监听开 #18 扬声器 (...)`。

> 供电与网络：三件套（识别/翻译/合成）都是云 API，需要能连 `token-plan.cn-beijing.maas.aliyuncs.com`。断网时本地识别仍会出字，但不出声。

**崩了会自己回来**：`run.bat` 现在是个守护循环——后端因为任何原因退出（包括内存不够 MemoryError），2 秒后自动重启，网页那边的 SSE 会自己重连，不用你重新点。连续崩 20 次才停手并打印提示。同时后端自带内存看门狗：占用过 900 MB 先把本地识别模型（228 MB）放掉，过 1500 MB 就主动重启自己（比被系统强杀干净）。想改阈值：控制台 `mem_soft_mb` / `mem_hard_mb`。

**只能起一个**：重复双击 `run.bat` 不会再起第二个后端（独占文件锁在用户目录 `out/vrdub.lock`），第二份会直接把浏览器指向已在跑的那个。

**日志**：所有日志写进 `%LOCALAPPDATA%\VRDub\out\srv.log`（单文件超 8 MB 自动改名 `.1` 并保留一份），控制台窗口关了也能事后查。

## 2. 三条链

```
                    ┌──────────── 我说话（A 链 · 出）
 麦克风 ──VAD──▶ 识别 ──▶ 翻译 ──▶ 合成 ──▶ CABLE Input ──▶ VRChat 麦克风 ──▶ 对方听到日语
   │                 ▲ 投机识别（说到一半就先送）        ▲ 说完前就开口
   └─ 字幕（浮窗/网页）

                    ┌──────────── 对方说话（B 链 · 入）
 扬声器 Loopback ──VAD──▶ 识别 ──▶ 翻译 ──▶ 字幕（只看不上屏，绝不回灌 chatbox）

                    ┌──────────── 对方打字（C 链 · 屏）
 屏幕区域 OCR ──▶ 识别 ──▶ 翻译 ──▶ 中文浮在原气泡位置
```

- **A 链**：我说话 → 日语出声。想换成**自己的声音**就录 10–20 秒样本点一下克隆（见下文「音色克隆」），克隆好的音色会出现在音色卡里，选中即用。TTS 用**克隆音色 t3**（`qwen-audio-3.0-tts-plus-t3-…`），对方听到的是「像我在说日语」。
- **B 链**：对方说话 → 中文。**译文只在本机显示**，不会进 VRChat chatbox。
  B 链的输入走 **Windows 进程回环**（`AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`）：只采 `VRChat.exe` 这个进程树的声音，所以你的麦克风、系统提示音、我们自己合成的日语监听都不会被当成「对方说话」再翻一遍。VRChat 输出继续走耳机，照旧听得见对方，不需要改声卡设置。日志应有一行 `[procloop] 进程回环开：PID xxxx ...VRChat.exe`。
- **C 链**：对方打字 → 中文**浮在原气泡的位置**上，停留约 4 秒再淡出（不打断视线、不用低头看角落）。
  默认是 **「按一下识别一帧」**（`ocr_mode=hotkey`）：**F5** 框范围、**F6** 抓当前这一帧、**F7** 切成常驻轮询。
  这样不占 CPU、也不会去读桌面上的字——VRChat 聊天框不动的时候，常驻轮询是纯浪费。
  语种不止日语：**自动 / 日 / 英 / 中 / 韩 / 俄 / 其它**（`cfg.ocr_src`）。自动=先本地认，认不出来才升级。
  本地只有中、日两套字库（中文字库连拉丁字母一起认），韩文/俄文/泰文这种字符集本地必然乱码，
  所以「认不出来」时用**视觉抄字**兜底：det 框照旧本地（DB 检测，跟语种无关，25–40 ms），
  只把「认字」这一步交给多模态模型（`qwen3.6-flash`，模型端点上的 qwen3-vl-* 全是 404，只有它能用），
  多花 0.6–1.0 s 换正确率；代价是那一帧慢一点，不是常驻开销。
  两道「本地白念了」的自动判据：字数比框宽应有的稀得多（换字符集了）、det 框住了宽正文却一个字都没认出来。
  三道防自反馈：原位浮现层、浮窗、弹幕窗口都调了 `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`——
  人眼看得见、抓屏看不见，否则 OCR 会把自己画出来的中文再识别一遍，屏幕上越翻越乱。
  同一屏幕位置用稳定 id（框重叠 ≥50% 就复用），同一行被切成几块会先横向合并，所以不会在同一处叠气泡。
  **默认不动任何一行**：屏幕上认到几个字就翻几个字（`ocr_label_strip=false`）——宁可多一行，也不猜哪行是噪声。
  只有把 `ocr_label_strip` 打开，才会剔掉气泡左上角那种「窄、短、没有句读」的说话人名字行。
- **CapsLock**：一键闭麦（对方听不到我，A 链停）。浮窗右上角红字「麦已闭」。
- **热键全表**：**小键盘 +** 识别一帧 / **小键盘 -** 框选范围 / CapsLock 闭麦 / **F7** C 链常驻开关 / **F8** B 链 / **F9** 清屏（F5/F6 同功能，留着备用）。
  小键盘加减号不跟任何常见软件抢键，这是选它们的理由。
  两条路一起用：先用 `RegisterHotKey` 让**操作系统直接派发**（日志会写「系统级注册：7 个」），哪个键被别的软件占了就自动退到 `GetAsyncKeyState` 轮询（20 ms + 粘滞位，10 ms 的轻点也不会漏）。
  热键是**全局**的，不抢焦点，VRChat 在前台也管用。**识别不受 C 链总开关影响**：C 链关着按一下也能识别，第一次会顺手把识别引擎叫起来（多等 1–2 s）。
  每次按下日志里都有一行 `[key] 按下 小键盘+`，`/api/state` 的 `key` 字段带最后按下的键与时间戳——按了没反应先看这两处。
- **弹幕**：A/B/C 三链的原文+译文会以双行弹幕从屏幕上飘过（日语青色、中文暗色），默认开。
- **chatbox**：只把 **A 链的日语译文**写进 VRChat 聊天框（整句定稿后发一次，144 字上限，5 条/5 秒限速）；B 链译文绝不进 chatbox。

### 音色克隆（用你自己的声音说日语）

控制台「音色」卡下面三个按钮，全程在这个页面里点，不用命令行：

1. **录音**：点一下，用**平时说话的音量**念 10–20 秒（不用念稿，随便说一段）。15 秒自动停。
   录完显示「3.0 s · 24 kHz · 峰值 0.89 · -28 dBFS」——**低于 -34 dBFS 会提示「声音偏小」**，说明麦克风选错或被别的软件占了，重录一次。
2. **试听样本**：把刚录的（已归一化成 24 kHz 单声道）从监听设备放一遍，确认不是噪声、不是别人在说话。
3. **克隆**：后台任务，进度条走云端状态（上传 → 训练中 → 就绪），一般 **10–40 秒**。成功后自动选中新音色，下一句就用它。

细节与坑：

- 样本要求：**24 kHz 以上、3–60 秒、单声道（自动转）、≤10 MB**；音量归一化到峰值 0.89（增益上限 +30 dB，救不了录音本身很烂的样本）。
- 服务商端点分两种：**套餐端点（token-plan）没有音色复刻模型**（真打会 404，Model not exist.），**按量端点（dashscope）有**。所以默认 voice_clone_endpoint=auto：先试套餐，遇到 404 就在本进程内记住、之后直接走按量，不再白跑。要强制指定就设 plan 或 payg。
- 克隆走按量端点时用 DASHSCOPE_PAYG_KEY（可能计费）；这个 key 没配就只剩套餐端点，克隆会失败——控制台「密钥」卡填的是套餐 key，按量 key 要在 .env.local 里另填。
- 录到静音**不会白花钱**：样本近乎静音（< -46 dBFS）直接拒，并提示「先确认麦克风选对了、对着它说话再录」。
- 克隆出的音色存在 %LOCALAPPDATA%\VRDub\config\settings.json 的 voices_custom 里（最多 24 个），音色卡上带 **×** 可以删（本地删 + 云端尽力删）。
- 音色只影响 **A 链（我说→日语）**；B/C 链是字幕，不合成。

### 人设（口吻）

音色卡下方是「人设（口吻）」：三张内置卡（自然口语 / テト活泼 / 敬语正式）点一下即生效，也可以在文本框里**自己写最多 1200 字**（例如「你在跟老朋友连麦打游戏，说话随意、偶尔吐槽、可以用『你』称呼」），点「保存」热生效。

人设**只管口吻，不管翻多少**：每张卡末尾都会自动追加一段硬约束（全译、不增、不减、不许省略概括合并、人称照原文、只输出译文、不许输出 (happy) 这类标签），写在前面也盖不掉它。人设只作用于 A 链，B/C 链（字幕）不受影响——否则对方的口吻会被你的设定污染。

### 识别引擎：两条链分开选

本地 SenseVoice（int8，60–150 ms）适合自己近讲，不适合远场/多人/唱歌；云端 qwen-audio 慢但准。所以两条链各有一个开关，控制台里 **A 卡、B 卡各一条「识别」下拉**，改完**下一段就生效，不用重启**：

| 链 | 默认 | 识别耗时（实测） | 适用 |
|---|---|---|---|
| A（我说 → 对方语种） | hybrid 本地优先 | 本地 31–103 ms，云端校正只改字幕 | 说话要快，句子短、近讲 |
| B（VRChat 里的人/歌 → 中文） | hybrid 本地优先 | 本地 79–351 ms（p50 79），云端后台校正 | 看字幕要跟得上说话 |
| B 对唱歌/远场更准 | cloud 云端 | 0.34–13.2 s（抖动极大） | 只在不介意等几秒时用 |

B 链原来默认走云端。2026-11-19 用 5 条日语素材做同一素材对比：**本地 143–351 ms，云端 340–13 236 ms，文本相似度 1.00（一模一样）**，所以默认改成 hybrid——字幕 p50 从 250–400 ms 降到 **80 ms**，最坏情况也从「偶尔等 1–13 s」变成「永远 ~150 ms 先出字、云端再校正」。

云端引擎下**投机识别不占链线程**（后台线程 + 同时只跑一条 + 最小间隔 asr_spec_gap 1.5 s + 单次超时 asr_spec_timeout 6 s），所以收尾永远不会被投机挡住：实测云端对 5–11 s 的长段/唱歌会飘到 6–19 s，串行跑就会把后面每句都堵死。
系统卡里那条「识别方式（两条链一起改）」是快捷方式，等价于同时改两个。

### 本地 GGUF 三档：真·离线、自带标点（可选）

云端慢、SenseVoice 不带标点也不判语种，所以除了「本地 /hybrid / 云端」，两条链的「识别」下拉里还多了三个**本地大模型档**。它们靠 [transcribe.cpp](https://github.com/handy-computer/transcribe.cpp)（ggml，CUDA/Vulkan）跑 GGUF 量化模型，控制台里选一下、下一段就换过去：

| 档（`asr_engine_*`） | 模型 | 体积 | 显存 | 实测单段 | 语种判定 | 标点 |
|---|---|---|---|---|---|---|
| `qwen17` | Qwen3-ASR-1.7B Q5_K_M | 1447 MB | 1441 MiB | 269–484 ms | 有 | 有 |
| `qwen06` | Qwen3-ASR-0.6B Q8_0 | 811 MB | 805 MiB | 354 ms（p50） | 有 | 有 |
| `fun` | Fun-ASR-Nano-2512 Q8_0 | 850 MB | 844 MiB | 386 ms（p50） | 无（要自己给语种） | **无** |

同一个 VRChat 现场（真人日语、16 段纯对话，对云端参考算 CER）：**1.7B 与 SenseVoice 的 CER 一样是 29.32%，但 1.7B 整句全对 3 段、SenseVoice 0 段**（SV 爱在句尾瞎补，`好きなんですけど` → `…けどしい`）；0.6B 36.73% / 全对 2；Fun 37.04% / 全对 2，且有把日语听成中文的毛病（`我不能不问`）。含唱歌的 22 段里 Qwen 系会整段吐英文歌词——当时以为「它至少判得出是英文」，后来 194 段全量测下来这个判断是错的（见下）。真机切到 `qwen17` 的现场字幕：`ありえない。ねえ、これねプヨプヨするね。` / `加害者えなんかさ結構なんかあのあのチョイスがさ攻撃的。`（159.8–356.3 ms，自带标点、无空段）。

| `qwen17` | 0.39 | 1.14 | 5 | 0 | **8** | 1 | 94.4 | 156 | 828 |
| `qwen06` | 0.48 | 1.21 | 7 | 1 | 0 | 3 | 92.5 | 133 | 290 |
| `fun` | 0.45 | 1.17 | 0 | 2 | 3 | **10** | 95.8 | 134 | 309 |

分条件（正常说话 / 唱歌 / 小声）：**正常说话 `qwen17` CER 44 最好**（SV 52、q06 63、Fun 58）；**一进唱段 `qwen17` 翻车**，假名比掉到 0.27、长度比 1.28（开始编）、CER 112 是 SV 的 2.9 倍；**SV 在小声碎段瞎补**（长度比 1.50）但 0 复读 0 漂移；Fun 一路瞎补（`无理取义忌高咧论`、`多少快活都来寻我干么`）。

`qwen17` 在 10 段唱段里有 **6 段直接写成英文或罗马字**：`Don't let them get you.` / `I finally found you, and I'm here now.` / `Muli tai, kikomeru.` / `But you.` / `The world will it ever reach?`，还有 1 段解码自重复（828 ms 整段丢）。**字幕里蹦英文、再被翻译成英文腔中文，比「听不清」更糟**，所以加了守卫：

> **语种漂移守卫**（`vrdub/asr.py`）：GGUF 档出字后先过 `util.lang_ok()`（ja 要假名 ≥15%、zh 要汉字 ≥45% 且假名 ≤10% 且拉丁 ≤55%），不对就用 SenseVoice 重听；重听结果语种正确就换掉，engine 记 `local(漂移)`；本地也漂就保留原结果，**绝不变成空字幕**。判据在 194 段极端素材上拦下 **107/117 段坏输出、误杀 0 段**（见下一节）。真值表 `tests/test_drift_guard.py`（7 组 18 项）。

另外 Fun 会把 `/sil` 当正文吐出来（`012032` → 整段只有 `/sil`），`asr_gguf.tidy()` 现在清掉这类标记，`silly`、`すし` 不误伤。

#### 全量复核（20261127 01:00–01:20，194 段，不再抽样，四家全上）

抽 30 段会骗人。这一窗是最极端的一段：连续 KTV 直播，**157/194 段 ≥6 s、121 段 ≥−20 dBFS**；云端自己都听不出 **40 段（21%）**（空返回最多重试 5 次），只有 154 段能算 CER。所以看**中位数**和**坏输出**，别看均值。

> **口径红线：GGUF 档必须带 language 提示。** 第一版脚本漏传（bench3.Engine.run 只传 task/timestamps），1.7B 因此整段整段吐英文——那是**测量错误**，不是模型缺陷。生产路径 vrdub/asr_gguf.transcribe() 一直是「先按 _LANG_HINT 传 ja，模型不吃才退回自动」，asr_gguf_hint 默认 auto。补测 language=ja 后同一批素材：1.7B 中位 CER **100% → 36.4%**、整句全对 **23 → 34**、英漂 **97 → 2**、p50 **268 → 158 ms**。下表全部是带提示的生产口径。

| 模型 | 中位 CER | 均 CER | 整句全对 | 空段 | 英漂 | p50 / p90 ms |
|---|---|---|---|---|---|---|
| SenseVoice | 45.5% | 70.4% | 20/154 | 29 | 0 | 437 / 452 |

| fun | 50.0% | 81.4% | 24/154 | 5 | **29** | 152 / 292 |

按场景拆（中位 CER / 整句全对）：

| 场景 | SenseVoice | qwen17 | qwen06 | fun |
|---|---|---|---|---|
| 唱 = 唱歌带 BGM（97–99 段可评分） | 57.1% / 3% | 50.0% / 12% | 56.0% / **14%** | **81.0%** / 10% |
| 说 = 正常说话（36 段） | 10.4% / 9 | **7.7% / 11** | 11.5% / 8 | 12.5% / 5 |
| 轻 = 小声碎片（19 段） | 15.8% / 8 | **0.0% / 11** | 9.5% / 9 | 9.5% / 9 |

- **唱歌段四家都救不了**（最好 50%），但 Qwen 系至少给的是日文、句子完整；qwen06 在这层整句全对最多（14 段）。

- **轻声层 qwen17 全对 11/19、中位 CER 0%**，比 SenseVoice（8/19、15.8%）明显好；代价是 1441 MiB 显存与 10 段空。

四条硬规矩：

1. **一次只驻留一个**：换档时先卸载旧模型再载新的（`asr_gguf.Resident` 里串行、带锁），日志会写「GGUF 切换：卸载 X → 载入 Y」。两个 GGUF 档同时驻留会直接吃掉 2.2–3 GB 显存，8 GB 卡上跟 VRChat 抢不起。
2. **两条链选了不同档**只驻留 B 链那个（B 是说话听得最多的通道），并 warn 一句。
3. **聊天框继承 B 链**：B 链用 GGUF 档时，聊天框文本就是这个模型的输出，不再额外花云端钱重听一遍（`chains._chatbox_src`）。
4. **GGUF 档不精修**：它自带标点与语种判定，anime-whisper（0.968）只会把好的擦掉。

#### 那下一句是日语还是英语？不用猜，逐段探

Qwen3-ASR 的输出协议是「先写一句 `language Japanese<asr_text>` 再写正文」——语种判定是它自回归的**第一个产物**，没有概率、不许反悔。所以我们钉一个提示，等于替它做了这个决定；钉错整句就换语种。411 段真实社交语料里：日语 343、中文 53、英语 **1**、其它 10、空 4 —— 主矛盾从来不是 ja vs en，而是 **ja vs zh**：钉 ja 时中文段会被**整句翻成日语**（`这里有别人的声音…` → `ここに別の人たちの声が聞こえます。`），中文段 CER 50.0% → 换成 zh 提示后 3.1%。

落地做法（`vrdub/asr.py` 的 `_lid_start` / `_lid_wait`）：解码的同时在旁路线跑一次 SenseVoice 的语种头（`LocalASR.lid()`，同一套 fbank/LFR/CMVN，`language=auto`，只读 `<|xx|>` 那个 token）。正常段**并行、零额外等待**；只有判定要换语种时才多跑一遍（~350 ms GPU）。

| 探测说 | 200 段实测 | 怎么用 |
|---|---|---|
| zh / yue | 精确率 **100%**、召回 75%、误报 0 | 默认就切（`asr_gguf_lid=zh`），中文段 CER 50.0% → 3.1%，ja 段 43.3% 纹丝不动 |
| ja | 精确率 99% | 它说 ja 就信 ja，不再折腾 |
| en / ko | **精确率 0–6%（不可信）** | 默认不认；`any` 模式下才认，或「钉 ja 却整句纯拉丁」时补一刀 |

因此：**默认 `asr_gguf_lid=zh`**（只救中文，绝不误切日语）；要连英语也自动照顾就设 `any`，代价是约 3% 的段落会白跑一遍重听（结果还要过 `lang_ok` 才采用）。残余风险已知且很小：英语句在 ja 提示下会被翻成日语（`Yes, I'm going.` → `すごい。`），这种「翻对了语种、翻了内容」的错脚本判据抓不到，只能靠探测头——而探测头对 en 不可信，所以英语场景靠 `any` 兜。

模型与运行库不进 git、也不在默认安装包里（3 GB + 1 GB）。换机器/给朋友装：

```bat
python tools\fetch_asr_models.py --check      :: 看缺什么
python tools\fetch_asr_models.py --all        :: 下模型（走 HF，可加 --proxy http://127.0.0.1:2080）
scripts\打包.bat                              :: 默认安装包不带 GGUF
python tools\build_exe.py --with-gguf         :: 要带就显式加（安装包会涨到 1.5 GB 以上）
```

CUDA 版的 `ggml-cuda.dll` 用裸名 `LoadLibraryA("cublas64_12.dll")` 找库，**只认 PATH、不认自己所在目录**，所以本机没装 CUDA Toolkit 时必须把 `cublas64_12.dll / cublasLt64_12.dll / cudart64_12.dll` 放进 `transcribe_cpp_native_cu12\_native` 并由 `asr_gguf._env_setup()` 把该目录前置进 PATH（`fetch_asr_models.py --runtime` 已经这么装）。缺了会报 `BackendError: backend error (status 8)`。

### 精修（refine）：定稿后后台再听一遍

快路（本地 SenseVoice）先把字幕顶上去，**定稿之后**后台再听一遍同一段音频，改了就把字幕刷掉——B 链连中文译文一起刷。开关在控制台 B 卡第二条「识别」下拉（`asr_refine`）：

| 值 | 行为 | 什么时候用 |
|---|---|---|
| `auto`（默认） | **云端优先**：云端没网/挂了/返回空，才把本地显卡模型拉起来 | 日常 |
| `cloud` | 只用云端 qwen-audio 精修 | 有网、要最准 |
| `whisper` | 只用本地 anime-whisper（CUDA） | 断网、要离线 |
| `off` | 不精修 | 想省那一遍算力 |

**为什么默认云端优先**：8 GB 卡上要跟 VRChat 抢显存，本地模型一常驻就是 1.1 GB；而它并不比 SenseVoice 更准（见下表），只在「有标点、离线可用」上占优。所以默认不常驻：云端失守时**只有它已经载入**才拿它兜底，不会为了一次抖动去占 1.1 GB 显存。要离线就把 `asr_refine` 直接设 `whisper`。

云端精修有 **6 s 上限**（`refine_timeout`）：实测它能飘到 13.2 s，那时候这段早念完了，等它没意义。

三路同一素材对比（`tools/_refine_ab.py` 干净 5 条 + `tools/_refine_hard.py` 5 条 × 噪声/混响/BGM/远场 = 20 组；相似度是跟「干净素材的云端文本」比）：

| 引擎 | 干净素材 | 劣化素材 | 单段耗时 | 显存 |
|---|---|---|---|---|
| 云端 qwen-audio-3.0-asr-flash | 1.000 | **1.000** | 1.4–5.2 s（最长 13.1） | 0 |
| 本地 SenseVoice int8（快路） | 1.000 | **0.992** | 0.25–0.32 s | 0（CPU） |
| 本地 anime-whisper int8_float16（CUDA） | 0.975 | 0.968 | 0.31–0.35 s（首次 13.9 s 建 kernel） | 1.1 GB |

结论也写进了选型文档：**「本地大模型」在这张卡上的价值是「离线可用 + 有标点」，不是「更准」**——噪声 5 dB 下云端 1.000、SenseVoice 1.000、anime-whisper 0.962；ja4 那条 anime-whisper 在四种劣化下都写成同音汉字（0.809–0.875），SenseVoice 0.920–1.000。

三条硬规矩（改这块别破）：

1. **精修耗时只写 `refine_ms`，绝不覆盖 `asr_ms`**——混进去会把识别 p50 整个拉歪（云端对一句话精修 9.5 s、一个字没改的段很常见）。
2. **<0.9 s 的碎片不精修**：云端对「喂」「嗯」要 9.1–9.5 s，改出来的差别只有一个逗号。
3. **精修不动已经排进 TTS 的音频**：只改字幕/译文，说话节奏不受影响。
4. **A 链（我说话→对面听日语）不享受精修**：`chains.py:379` 定稿识别一出来就同步 `_translate_speak`（翻译+入队 TTS），`_refine_async`（`chains.py:635`）是之后才跑的后台任务，改的是**已经念出去那句**的字幕。所以 A 链要提质只能把更准的识别放到翻译之前（`_cloud_now` + `cloud_wait` 那条同步二次确认），不能在精修上找。精修的收益全在 B 链字幕（B 链不出声，改了不重念）。

### 引擎怎么选：注册表 + 机器条件（换机器不改代码）

这个项目要能搬到别人机器上跑，所以「用哪个模型」不写在代码里，写在 [vrdub/asr_engines.py](vrdub/asr_engines.py) 的规格表里。每条引擎声明：支持哪些语言、多大、要多少显存/内存/几核、实测延迟区间、实测质量分、能不能离线。

选档规则（`asr_engines.pick(lang)`）：

1. 先按**语种**筛：只在这个语种支持的引擎里挑（`whisper-anime` 只做日语，中文根本不在候选里）；
2. 再按**装不装得下**筛：显存/内存/核数不够的直接排除，并给出原因（「要 1100 MB 显存，现在只空 300 MB」）；
3. 剩下的按「实测质量优先、延迟次之」排序；
4. **cfg 里手写就听 cfg 的**：`asr_engine_map`（按语种）> `asr_local_engine`（全局）> 自动。

所以同一份代码在不同机器上会自动给出不同答案：8 GB 卡 + VRChat 同跑时中文/日语都只能挂 SenseVoice（0 显存）；12–16 GB 卡可以把日语档换成 `whisper-anime`（带标点）；纯 CPU 机器照样跑 SenseVoice。

看当前机器会跑什么、为什么（不用启动服务）：

```
python tools/asr_ab.py --list
```

接口里也能看到：`/api/state` → `asr.pick = {"zh": "sensevoice", "ja": "sensevoice"}`、`asr.host` 是当时探到的机器条件（核数 / 内存 / 空闲显存）。

### 质量靠真话来测，不靠合成素材

`out/clips/*.wav` 是 TTS 合成的干净音频——拿它测引擎，所有引擎都是 1.00，那测的是「读不读得懂清晰合成音」，不是「我在 VRChat 里说话它听不听得清」。真判据只能用真人真麦真房间的音频，所以加了两块：

| 键 | 作用 |
|---|---|
| `asr_capture`（默认 false） | 每条定稿段落连同识别文本存到 `out/corpus/<日期>/`（wav + json），正常说话就会攒 |
| `tools/asr_ab.py` | 在攒下的真话上 A/B 两个引擎：`python tools/asr_ab.py sensevoice whisper-anime` |

`asr_ab.py` 逐条打印两条引擎的耗时与互相相似度，**相似度 < 0.9 的那几条单独标出来**——那才是值得人耳判断的句子（一致的部分不用听）。汇总给均值 / p90 / 与线上引擎一致率。

## 3. 延迟是怎么花掉的（实测，不是估计）

| 环节 | 实测（12:59 评测，n=4 句） | 说明 |
|---|---|---|
| 本地识别（投机，说到一半先送） | **110–500 ms** | 本地 SenseVoice，只为「字幕先出字」，不阻塞出声 |
| 云端识别（收尾/校正） | 280–2 800 ms（抖动很大） | 决定最终原文，**不挡 TTS**：句尾一到就用投机结果先翻先念 |
| 翻译首子句 | **p50 289 / p90 364 ms** | `qwen3.6-flash`，SSE 流式，子句一出来就交给 TTS |
| TTS 首包 | **p50 867 / p90 1 198 ms**（地板 ~750 ms） | `qwen-audio-3.0-tts-plus`，与文本长度基本无关 |
| **句尾 → 日语开口（A 链）** | **p50 463–1 381 ms / p90 1 112–2 725 ms** · 最快 167 · 最慢 3 119（8 次评测区间） | 中位数已经贴着 TTS 首包地板再加半个气口；部分句子为负（我还没说完就开口了） |
| **起话 → 日语开口（A 链）** | p50 2.6 s / p90 3.7 s | 含我说话的时长（一句话本身 2–4 s），所以短句体感几乎「同传」 |
| **对方说完 → 中文字幕（B 链）** | **p50 300 ms / p90 313 ms** | 只出字幕不出声；长句为负（字幕先于对方句子结束就上屏） |
| 精修（后台第二遍，不改上面的数） | 云端 1.4–9.5 s · 本地显卡 0.31–0.35 s | 只刷字幕/译文，不挡字幕也不挡出声 |
| 屏幕气泡 → 中文（C 链单帧，日/英/中） | **本地识别 190–350 ms + 翻译 ~300 ms** | F6 按下去到中文浮现，实测 480–580 ms |
| 屏幕气泡 → 中文（C 链单帧，韩/俄等视觉抄字） | **识别 0.9–1.2 s + 翻译 ~300 ms** | 换字符集只能走多模态，多花 0.6–1.0 s |
| 屏幕气泡 → 中文（C 链常驻轮询） | 轮询 350 ms + OCR ~100 ms + 翻译 ~300 ms | 稳态一屏一改，不追 60 fps |

**想更快**：控制台把「句尾静音」从 0.50 s 调到 0.35 s（每快 0.15 s，代价是有人说话带停顿会被切成两句）。
**想更准**：把「最少提交字数」从 8 调到 12，碎句更少、出话稍晚。

## 4. 翻译质量（这套系统的重点）

- **人设只管口吻，不管翻多少**：每张卡都带硬约束——全译、不增、不减、不许省略概括合并、人称照原文、只输出译文。默认卡 natural（自然口语，不强制「俺」），另有 polite（です・ます）和 teto（活泼）；也可以自己写最多 1200 字自定义口吻（见 §2「人设（口吻）」）。
- **碎片不单翻**：只有遇到真标点或明确的语气末（了的吗呢啊呀吧…）才切；4 字碎片会被模型猜错（实测「自然多了」→「違う」），所以宁可等半秒。
- **收尾整句重译**：句尾一定用完整原文再翻一次，和已经念过的部分求公共前缀，**只补没念过的尾巴**；字幕永远替换成整句译文（只增不减）。
- **上下文只作参考**：最近 200 字上文单独喂给模型，并明确「绝对不要翻译上文」。
- **重复抑制**：和上一片相似度 > 0.86 的译文不重念。
- **静音幻觉闸**：整段 95 分位比门限还低 6 dB 就不送识别（实测静音送云端会「听出」一句根本不存在的中文）。
- **目标语校验**：译文送出去前先验语言——日译必须真有假名，中译不许夹假名/英文，不达标先按「必须 100% 是日语、不许夹英文」重翻一次，还不行这句就不出声（只留原文）。踩过的坑：UI 把 A 链目标语误设成「中文」，模型中文→中文原样回吐，chatbox 里全是中文，看着像翻译坏了——现在目标语只允许 日/英/韩，中文由 B/C 链负责。
- **标注/情绪标签全清**：模型偶尔吐 `(happy)…(end)`、`[笑]`、`*叹气*`、`<emotion>`，会被 TTS 念成 "happy / end"。现在两层清洗：翻译结果过 `util.strip_anno`（成对括号短标注、星号强调、开头/结尾孤立标签词），TTS 请求前再清一次，人设里也明确禁止输出标签。
- **回声/漏音：只拦真回声，绝不吞复述**（2026-11-19 重写）。主判据是**波形匹配滤波**：把麦克风那一段和刚刚放出去的音频做归一化互相关——真漏音是同一段波形（电学回路实测 0.98），「同一句话再说一遍」是另一场演奏（实测 <0.05）。阈值：相关 ≥0.15 且麦克风不比播放响（能量差 <+6 dB）才丢。旧的「文本相似度 >0.6 就算回声」已彻底删除，那是「疑似自己的回复」误杀复述的根源（日志实证同一句连丢三次）。
  辅助闸：① A 链收到日语但我说的是中文（目标语不是中文时才判）→ 丢；② 和 B 链 6 秒内文本高度相似 → 丢；③ 短促噪声幻觉（<0.55 s、≤3 字、低于门限 +9 dB）→ 丢。
  电平/包络类的两道闸（`leak_gate`、`bleed_lvl`）**默认关闭**——VRChat 声音比麦克风响时它们必然触发，实测一天吃掉 40+ 段真话。

## 5. 掉链排查

| 现象 | 看这里 | 处理 |
|---|---|---|
| 控制台右上角是「连不上后端 · 第 N 次重试」 | 后端没起或正在重启；双击桌面「VRDub 无言势」，它会拉起后端再开页面 | 页面**不会**拿假数据顶替：离线预览只在「本地 html 文件直开」时出现，那时角标会写「离线预览」且所有操作都不真的发出 |
| 控制台打不开（浏览器「无法连接」） | `%LOCALAPPDATA%\VRDub\out\keepalive.log` 与 `srv.log` 尾部 | 先看后端还在不在：`Get-NetTCPConnection -LocalPort 8899`。**电脑睡过一觉 / 重启过，后端会跟着没**（2026-11-20 14:23 就是这样：事件 42 进入睡眠，run.bat 一起断了，睡了 13 小时）。现在有计划任务 `VRDUB-Sync`（登录时触发、之后每 5 分钟）跑 `scripts\keepalive.ps1`：端口没监听就自动把 `run.bat nobrowser` 拉起来。手动补一次：`powershell -NoProfile -ExecutionPolicy Bypass -File scripts\keepalive.ps1`；不想要自启就 `Unregister-ScheduledTask -TaskName VRDUB-Sync` |
| 控制台打不开（页面能开但是白的） | 浏览器 F12 的 Network | 页面本身是静态壳子，样式和脚本走 `/static/style.css`、`/static/app.js`；这两个 200 才算正常（各约 31 KB / 68 KB）。根路径下的 `/app.js`、`/style.css` 本来就该 404，壳子会自己回退到相对路径 |
| 「麦克风打不开」 | 控制台红色徽章 + `out/err.log` | 设备被别的软件独占（VRChat / Discord / OBS）；关掉占用者，或在设备下拉里换一个 |
| 对方听不到日语 | 「试听」有没有声 | 没声 = 输出设备不是 `CABLE Input`；有声 = VRChat 麦克风没选 `CABLE Output` |
| 日语一直不说 | 表格里 A 链段停在 `mt`/`tts` | 网络或额度；看日志里的 `HTTP 4xx` |
| 重启后声音串了（日语放给自己听 / 对方一句没收到） | 启动日志的三行 `播放开` `监听开` `采集开 mic` | Windows 每次启动重排设备序号，**号码还活着、通道数也对，校验拦不住**。现在按**名字**绑（`dev_names`）：正确应看到 `播放开 #n CABLE Input`、`采集开 mic #n 麦克风 (你的耳机)`、`监听开 #n 扬声器`。名字对不上时控制台重选一次设备即可（重选会同时记住名字） |
| 精修很慢又没改字 | `/api/state` 的 `last[].refine_ms` | 云端精修抖动可达 9 s；急的话把 `asr_refine` 设 `off`，或设 `whisper` 用本地显卡（0.31–0.35 s，代价 1.1 GB 显存） |
| B 链没反应 | 先看 `/api/state` 的 `loop.alive` | `false` = 没连上 VRChat（日志「VRChat 进程回环没连上」）；`true` 但 `stat.blocks` 不涨 = VRChat 没在出声；想退回设备采集就把 `loop_src` 设成 `device` |
| C 链不认识字 | 控制台 C 卡区域 | 点「框选区域」只框气泡那一块，别整屏（整屏会降频到 2 s 一帧） |
| 声音一顿一顿 | `out/bench.md` 的实时率 | 实时率 > 1 说明合成跟不上说话速度，把语速调 1.1 或人设换短句 |
| B 链整段没字幕、日志全是「太安静弃段」 | 日志里的门限行 | 放歌/连续人声时本底很高，旧版会把门限顶到 -18 dB 把正常句子全丢掉（已修：上界 -30 dB，音源吵时门限贴本底）。仍然丢就手动 `cfg loop_db=-30` |
| A 链把我的话翻成乱七八糟 | 日志里 `收到日语（我说的是中文）` | 耳机漏音被麦克风收进去了（它以为是我在说日语）。这段会被直接丢掉；要么戴紧耳机、要么把系统音量降一点 |
| chatbox 里冒出别人的歌词 | 日志 `[osc] chatbox` | 旧版出声关着也会发（已修：只有真的念出来、且不是回声/漏音时才发） |
| **我说的话偶尔被吞（同一句重说就没反应）** | 控制台里那段是不是 `drop`，日志写的原因 | 2026-11-19 已重写回声判定（波形匹配替掉文本相似度），复述不会再被吃。若还丢：看日志是「噪声短语」还是「收到日语」——前者是声音太轻/太短，后者是耳机漏音 |
| 想知道为什么某段被丢 | 段上的 `note` 字段（控制台悬停） | 现在每条丢弃都写实测依据：`这是自己的声音漏回麦克风：波形与自己刚放出去的声音 0.98 相同（偏移 -446 ms）` |

## 7. 已知限制

1. **TTS 首包 ~750 ms 是云 API 的地板**，任何「1 s 以内」的说法都是指「说完之后」；起话到开口必然叠加我说话的时间。
2. **云端识别会抖**（370 ms 到 2 s）。所以先出声用的是投机结果，最终原文可能被改写 1–2 个字（控制台会看到 `asr`/`refined` 两态）。
3. **碎句风险**：如果一句话里停顿很多，前几片可能被单独翻译，导致日语读起来像碎裂的短句（字幕是整句的，不受影响）。
4. **C 链依赖屏幕**：分辨率或 UI 缩放变了要重新框选（F5）；日文假名小写（っゃゅょ）靠词表后处理纠正，不是 100% 准。
   韩/俄/泰这类字符集本地没有字库，走视觉抄字（慢 0.6–1.0 s）；框选范围里如果混进了别的窗口文字，它也会一起翻——框小一点更干净。
5. **单机单实例**：PortAudio 全局单例，不要同时开两个后端进程。
6. **C 链（屏幕 OCR）还没做好**：链路是通的（框选→截图→识别→翻译→浮窗原文），但只在小窗口截图上验证过；跟着画面变化连续识别、原文浮回原位、多语种切换、游戏内 HUD 遮挡都还没调稳。所以默认 **`ocr_on=false`**。现状与缺口记在 `docs/待修清单.md` 第 4 条。
7. **音色克隆还不完善**：录音→转码→上传→训练轮询→切音色这条链能跑通，但样本处理只做了「下混 + 24 kHz 重采样 + 峰值归一（上限 +30 dB）」，没有降噪、没有静音裁边、没有多段拼接；克隆音色在长句/情绪句上的稳定性也没做过主观评测。另外**套餐 key 不支持音色复刻模型**（HTTP 404 `Model not exist.`），会自动转按量 key，没配按量 key 就会失败。
8. **没有托盘、没有自更新**：退出就是关掉后端；升级要重新下安装包（配置和日志在用户目录，不会丢）。
9. **GGUF 三档默认不在安装包里**：运行库（transcribe_cpp + CUDA 版 DLL）1.0 GB、三个模型 3.1 GB，全塞进去安装包会从 264 MB 涨到 1.5 GB 以上，所以默认只装 SenseVoice（252 MB）。要用 Qwen3-ASR / Fun-ASR：跑一次 `python tools\fetch_asr_models.py --all`，或者自建时用 `tools\build_exe.py --with-gguf`。另外 **CUDA 版本吃显存档位**：1.7B 常驻 1441 MiB，VRChat 自己在 8 GB 卡上已经占 4.4–4.6 GB，切之前先看一眼控制台「系统」卡里的显存。
10. **一次只能驻留一个 GGUF 档**（这是设计，不是缺陷）：切档要重新载入，1.7B 约 2.8 s，期间那一段识别走本地 SenseVoice 兜底。

## 8. 仓库与分发

这是个**正常 git 仓库**（`main` 分支，历史从 0.9.0-dev 起），不是「一堆文件打包」。

**仓库里有什么**：源码 `vrdub/`、脚本 `scripts/`、工具 `tools/`、真值表 `tests/`、文档 `docs/`、模型配置与词表、`pyproject.toml` / `requirements.txt` / `CHANGELOG.md`。提交只有 1.5 MB 量级。

**仓库里没有什么**（`.gitignore` 挡住）：权重 `models/**/*.onnx|bin`、虚拟环境 `.pylibs/ _pylibs*/`、运行产物 `out/ dist/`、日志、以及**任何密钥**——`.env.local` 永不入库，模板是 `.env.example`。

**别人拿到手怎么跑**：

```bat
git clone <仓库地址> vrdub && cd vrdub
py -3.12 -m venv .venv && .venv\Scripts\pip install -r requirements.txt
python tools\fetch_models.py --check     :: 缺什么会列出来
copy .env.example .env.local              :: 填自己的 DASHSCOPE_TOKENPLAN_KEY
run.bat
```

模型权重（228 MB + 9 MB）放 GitHub Release 附件或网盘，解压到 `models/` 即可；`tools/fetch_models.py` 能自动下 OCR 那两个。

**他的配置与他自己的 key**：默认读 `%LOCALAPPDATA%\VRDub\config\`，跟我们本机完全隔离；他的设备序号、他的 key、他的日志都在他自己的用户目录里，不会串。

### 密钥：仓库和安装包里永远没有

这一点是硬约束，不是习惯：

- **代码里没有任何 key**。key 只从一个文件读：`%LOCALAPPDATA%\VRDub\config\.env.local`，这个路径被 `.gitignore` 排除，`packaging\vrdub.iss` 也不打包它（安装包里只有 `.env.example` 形状说明）。
- **安装包 exe 不内置 key**：朋友装完是「未配置」状态，云端功能不可用，本地识别照常出字。
- **朋友怎么填**：装完打开控制台 → 右侧「密钥」卡 → 粘贴你给他的 key（`sk-` 开头）→ 保存。保存时后端会真的打一次 `max_tokens=1` 的 chat 请求做自检，返回「自检正常」才算通，**不用重启**。也可以直接写 `.env.local`（`DASHSCOPE_TOKENPLAN_KEY=sk-他自己的key`）。
- **自查有没有漏**（提交前、发包前都能跑）：

  ```bat
  git grep -n -I -e "sk-" -e "gho_" -e "DASHSCOPE_TOKENPLAN_KEY=sk-"
  ```

  只应命中 `.env.example` 里的占位符。
- **按量 key 是可选的**：只有音色克隆（复刻模型）需要它；不配就只影响克隆，其它功能都走套餐 key。

### 给朋友一把「不是主密钥」的钥匙

三条路，详见 [docs/子密钥网关.md](docs/子密钥网关.md)：

1. **原生多 key（先试这个）**：百炼控制台能建多把 API Key（账号+地域最多 50 把），可归属 RAM 用户、可配 IP 白名单与模型白名单（最多 30 个模型）。套餐额度按账号算，多把 key 共用同一份余量。
2. **RAM 用户**：要「一刀切停掉这个人」或「分账」时，建 RAM 用户、把 key 归属给他，停用户即可。
3. **自建子密钥网关**：控制台确实只放一把 key 时，跑 `python tools\relay.py` —— 主密钥留在你机器上，朋友用 `sub-…` 打你的网关（校验、白名单、每日配额、记账、SSE 原样转发）。对方在「密钥」卡里把端点填 `http://<你的地址>:8787` 即可。

## 9. 打成安装包（给朋友的那种）

`scripts\打包.bat` 一次做完三件事：PyInstaller onedir → 复制模型 → Inno Setup 出安装包。产物 `dist\installer\VRDub-<版本>-setup.exe`。

| 项 | 实测值 |
| --- | --- |
| 安装包 | **264.5 MB**（lzma2/max 压缩，耗时约 3.5 min） |
| 装完占地 | **591 MB**（程序 + `_internal` + 内置模型 252.7 MB） |
| 首次启动 | 3–5 s 载入 SenseVoice，随后 `/api/health` 就绪 |
| 装在哪 | `%LOCALAPPDATA%\Programs\VRDub`（默认，可选） |
| 用户数据 | `%LOCALAPPDATA%\VRDub\`，卸载时问一句要不要一起删 |

**安装包里有什么**：`VRDub.exe`（同目录 `_internal\` 是 Python 3.12 与 8 个依赖）、`models\` 里识别的 8 个权重、网页控制台、图标与版本资源。朋友不需要装 Python、不需要配 `PYTHONPATH`、不需要 `pip`。

**安装包里没有什么**：任何密钥。装完第一次开要填一次 key（网页控制台底部「密钥」卡，粘贴 + 保存 → 自动写进 `%LOCALAPPDATA%\VRDub\config\.env.local` 并当场自检 HTTP 200）。

**子进程怎么起**：`hud / danmaku / ocr_overlay / region_picker` 都是同一个 `VRDub.exe --child <名字>` 再进来一次（`vrdub/child.py`），所以打包后不会有「找不到 python.exe」也不会闪黑框。

**改代码之后怎么重打**：`scripts\打包.bat`（会先删旧的 `dist\exe`）。只想看界面就 `run.bat` 跑源码，两条路共用同一套用户目录。
